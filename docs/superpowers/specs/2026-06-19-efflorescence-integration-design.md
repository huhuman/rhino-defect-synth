# Efflorescence: procedural material integration (design + decision needed)

Generator (built + tested): `tools/efflorescence/efflore_synth.py`. Produces, per sample,
`albedo` (deposit-over-concrete) + `alpha`/`coverage` (continuous) + `label` (binary, exact) +
`roughness`. The coverage mask is exact-by-construction (verified: target coverage == actual).

This doc covers wiring it into the Rhino component pipeline and the one decision it forces.

## Current efflorescence flow (what we're replacing)
- Material: a real efflorescence PHOTO is selected per efflore layer (`component_base.yaml` efflore
  material lists) and applied via `apply_efflore_texture_mapping` (texture_mapping.py:525,
  world_orthogonal UV) onto the efflore top faces. Geometry built in
  `defect_placement_efflore.py:67` (inner/outer extruded polygons → layers `defect::efflore::CS2`,
  `CS3::inner`, `CS3::outer`).
- Label/mask: produced by the `CaptureBaseColorMask` plugin.

## KEY FINDING — the mask ignores material/opacity (decision driver)
`CaptureBaseColorMaskCommand.cs` builds a render mesh per object, sets **every vertex to the flat
layer colour**, and draws it with `DrawMeshFalseColors` — **no lighting, no texture, no opacity**
(CaptureBaseColorMaskCommand.cs:256-363). So the efflore mask is **always the full geometry
footprint in the layer colour**; it cannot reflect the procedural alpha coverage.

Consequence: simply swapping the photo for the procedural albedo makes the *colour render* realistic,
but the *label* still covers the entire efflore polygon — including feathered edges and gaps where
concrete shows through. That is an OVER-complete label (the mirror of today's incomplete one).

## The decision
**How accurate must the efflorescence label be?**

- **Option A — interim (appearance now, approximate label).** Replace the efflore layer material with
  the procedural albedo (white deposit over concrete, feathered). Keep the full-polygon mask. Make
  the generator default to HIGH coverage with only edge feathering so over-labeling is small.
  - Pros: small, fast; big realism win immediately; no plugin change. Testable in one run.
  - Cons: label still ~full-polygon, not pixel-exact.
- **Option B — exact label (recommended end state).** Also teach the mask to honour the deposit
  coverage. Cleanest: extend `CaptureBaseColorMask` to, for efflore objects carrying a coverage
  texture, modulate the drawn mask by the alpha (draw only where coverage>=0.5, else leave
  background/under-layer). Then the procedural alpha IS the label — pixel-exact, the whole point.
  - Pros: solves the labeling complaint exactly. Cons: C# plugin change + rebuild + test.
- **Option C — bake coverage into geometry.** Model the deposit as geometry matching the coverage
  footprint so the full-geometry mask already equals coverage. Heaviest; not recommended.

**Recommendation: A now (to see realism in your single test run), then B for the real fix.** A and B
share the same generator and material wiring; B only adds the plugin-side alpha modulation.

## Integration seams (from the code trace)
1. **Offline library** (no Rhino): `tools/efflorescence/` — pre-generate a pool of albedo+alpha PNGs
   (vary seed/coverage/hardness). Store under the texture root. The alpha PNG is also the label asset
   for Option B.
2. **Material wiring** (`pipeline.py:prepare`, after material selection ~line 189): for the three
   efflore layers, build a PBR RenderMaterial whose Base Color = a generated efflore albedo and whose
   Opacity = its alpha (so the colour render shows concrete through the gaps), and assign it to the
   layer (the existing `layers.create_layers` already sets `layer.RenderMaterial`). A new
   `materials.create_efflore_procedural_material(albedo_png, alpha_png)` factory is the clean seam.
3. **Texture mapping** (`apply_efflore_texture_mapping`): unchanged — world_orthogonal UV maps the
   procedural maps onto the efflore top faces.
4. **Mask** (`CaptureBaseColorMaskCommand.cs`): unchanged for A; for B, modulate the false-colour draw
   by the object's coverage texture (sample alpha per fragment / threshold) so the mask = coverage.

## Why this beats photo-paste either way
The deposit is "base concrete + thin white coating" (correct physics), the substrate reads through,
and (Option B) the label is generated by the same mask that places the deposit — no annotation/photo-
edge mismatch. See `docs/research/2026-06-19-efflorescence-material.md`.

## Option A — runnable now (assets + config, ZERO pipeline code)
The deposit maps are named for `texture_naming.MAP_SUFFIXES`, so the existing texture-seed importer
auto-wires them (color→albedo, opacity→opacity, roughness→roughness). To try it:

1. On the Windows machine (has the Rhino texture_root), generate the library INTO the texture root:
   ```
   python tools/efflorescence/efflore_synth.py --mode library --count 24 ^
       --size 1024 --out "C:/Users/shh/Documents/ShunHsiangHsu/DefectSynthetic/Textures/efflore_proc"
   ```
   (texture_root_dir is searched recursively, so a subfolder is fine.) It prints the stems to use.
2. In `configs/component.local.yaml`, replace the efflore layer material option lists with those
   stems, e.g.:
   ```yaml
   modeling: ... (materials live in component_base.yaml; override there or in .local)
   "defect::efflore::CS2":        [efflore_000, efflore_001, efflore_002, ...]
   "defect::efflore::CS3::inner": [efflore_000, efflore_001, efflore_002, ...]
   "defect::efflore::CS3::outer": [efflore_012, efflore_013, ...]   # heavier coverage set
   ```
3. Run a single batch. The colour render now shows a white deposit over concrete (transparent in the
   gaps via the opacity map). Label stays full-polygon (Option B upgrades that).

If it looks wrong, revert the material lists — no code paths changed. Note: `opacity` makes the
deposit transparent in gaps, so the efflore top face shows whatever is behind it; verify that reads
well against the bridge surface, and tune coverage/hardness in the builder if needed.
